## 1. 产品定位（增量）

### 一句话定位

**AI 调解员小程序版 — 双人协作调解室：让冲突双方各自上传证据，AI 匿名仲裁，给出谁更有理、为什么、下一步怎么和解。**

### 从"单人裁判"到"双人协作调解室"

| 维度 | Web 版 | 小程序版 |
|------|--------|----------|
| **参与模式** | 单方上传，单方查看 | 双人协作：甲方创建案例 → 乙方扫码加入 → 各自上传 |
| **证据来源** | 仅有发起方提供的截图 | 双方各自上传己方视角的聊天记录，证据更完整 |
| **公正性** | 依赖单方证据，可能有选择性偏差 | 双方证据交叉验证，AI 判断更客观 |
| **身份体系** | 无登录（本地存储） | 微信登录 + openid，区分甲方/乙方 |
| **协作机制** | 无 | 邀请卡片/二维码 + 提交状态双向可见 + 提交完成自动分析 |
| **分享能力** | 无原生分享 | 微信原生分享卡片至聊天/朋友圈 |
| **隐私控制** | 无（单人使用无所谓） | 分析结果"双方可见" vs "仅发起方可见" |
| **追问体验** | Web Chat UI | 原生聊天界面风格追问 |

### 增量价值

小程序版解决 Web 版的核心痛点：**单方证据的不完整性极大削弱了分析可信度**。通过双人协作机制，小程序版将 AI 调解员从"单方裁判工具"升级为"双方认可的客观调解室"。

### 目标用户增量

- **Web 版**：情绪受害者小林（自己看）、理性调解者老王（替别人分析）
- **小程序版新增**：争议中的双方（小林 + 吵架对象），调解者老王邀请双方加入

### 用户故事列表

#### P0 — 核心协作体验

| ID | 用户故事 |
|----|---------|
| US-M01 | 作为**冲突中的小李**，我想**微信一键登录后创建新案例**，这样我不需要注册账号就能开始使用 |
| US-M02 | 作为**发起方小李**，我想**将案例通过微信分享卡片发给小王**，这样小王能一键加入协作 |

## 3. 需求池

### P0 — Must Have

| ID | 需求 | 描述 | 验收标准 |
|----|------|------|---------|
| **P0-M01** | **微信登录 + 身份识别** | `wx.login()` 获取 code → 云函数换取 openid → 作为用户唯一标识。首次使用时调用 `wx.getUserProfile()` 获取昵称头像。区分"甲方（案例创建者）"和"乙方（受邀加入者）"。 | 1. 打开小程序自动静默登录 2. openid 作为 user_id 持久化 3. 案例中正确标注甲方/乙方身份 |
| **P0-M02** | **案例创建** | 创建案例时设置：案例标题（可选，默认"调解案例"）、关系类型（情侣/朋友/同事/家人/其他，可选）、隐私设置（双方可见 / 仅发起方可见）。案例创建后自动生成邀请码（6 位数字或短链）。 | 1. 创建流程 ≤2 步 2. 自动生成唯一邀请码 3. 支持关系类型和隐私设置 |
| **P0-M03** | **邀请机制** | 生成微信分享卡片（`wx.shareAppMessage`）包含案例标题 + 邀请码。支持转发到聊天（onShareAppMessage）和生成小程序码（`wxacode.getUnlimited` 云函数）。 | 1. 分享卡片展示案例标题和识别信息 2. 对方点击/扫码后直接进入案例 3. 邀请码唯一且可识别 |
| **P0-M04** | **双人独立上传证据** | 甲乙方各自上传聊天截图。上传方式：①微信原生选择聊天记录（`wx.chooseMessageFile` 选 txt）或 ②相册选择截图。OCR 解析后显示预览，确认后提交。**在对方也提交之前，自己提交的内容对对方完全不可见。** | 1. 双方各有独立上传入口 2. 上传后本地预览 OCR 结果 3. 对方提交前看不到内容 4. 提交后不可修改（除非重新上传覆盖） |
| **P0-M05** | **提交状态同步** | 案例详情页实时显示双方状态：甲方（你）| 乙方：未加入 → 已加入 → 待提交 → 已提交 → 分析中 → 分析完成。使用云数据库 `watch` 实现实时状态更新。 | 1. 状态变更 ≤3s 内同步到对方 2. 双方都提交后自动触发分析（或显示"开始分析"按钮） 3. 分析进度实时可见 |
| **P0-M06** | **AI 分析触发** | 双方都提交证据后，云函数合并双方聊天记录 → 调用 DeepSeek/Claude API → 生成 v2 Analysis 结构。支持自动触发（双方提交后自动开始）或手动触发（任一方点击"开始分析"）。分析过程中显示 CoT 进度（理解→证据→情绪→判断→策略）。 | 1. 双方提交后 5s 内自动触发分析 2. 分析进度可实时查看（云函数 push 进度到数据库） 3. 分析结果存储到云数据库 4. 任意一方触发后另一方不需要重复触发 |
| **P0-M07** | **分析结果查看（隐私控制）** | 根据创建时设置的隐私策略：①"双方可见"→ 甲乙双方都能查看完整报告 ②"仅发起方可见"→ 乙方只能看到"分析已完成，结果仅对发起方可见"的提示。报告页面适配移动端 4 层递进结构（核心结论→证据→策略→详细分析）。 | 1. 双方可见模式下双方都能看到报告 2. 仅发起方模式下乙方不可见 3. 报告 4 层结构在小程序中正确渲染 |
| **P0-M08** | **云数据库设计** | 设计 `cases` / `evidence` / `analyses` 三个核心集合，以及 `invitations` 辅助集合。Schema 见 §5.2。 | 1. 所有集合可通过云函数 CRUD 2. 权限规则：用户只能读写自己参与的案例 3. evidence 字段级别的读写隔离 |
| **P0-M09** | **聊天式追问** | 报告页底部提供聊天式追问界面，风格模仿微信聊天。追问时将 v2 Analysis JSON 作为上下文传给 LLM。支持 SSE 流式输出（通过云函数 + WebSocket 或轮询模拟）。 | 1. 追问界面为原生聊天风格 2. AI 回答流式渲染 3. 引用报告中的证据和情绪数据 |

## 5. 云开发架构概要

### 5.1 云函数列表

| 云函数 | 触发方式 | 职责 | 可复用代码 |
|--------|---------|------|-----------|
| **`login`** | HTTP 调用（`wx.login` 后） | 接收 code → `auth.code2Session` 获取 openid → 返回自定义登录态 | 无（纯微信云开发逻辑） |
| **`createCase`** | HTTP 调用 | 创建案例记录，生成邀请码，写入 `cases` + `invitations` 集合 | 无 |
| **`joinCase`** | HTTP 调用 | 根据 inviteCode 加入案例，更新 `cases.party_b`，触发状态变更通知 | 无 |
| **`uploadEvidence`** | HTTP 调用 | 接收文字/OCR 后文本，写入 `evidence` 集合，更新案例提交状态 | `parser.ts` (parseWeChatChatLog) |
| **`analyzeCase`** | HTTP 调用（双方提交后自动或手动触发） | 合并双方 evidence → 格式化聊天记录 → 调用 LLM API → 写入 `analyses` 集合 | `llm.ts` (analyzeChat) + `analysisPrompt.ts` + `parser.ts` (formatChatForLLM) |
| **`chatWithAnalysis`** | HTTP 调用（SSE 流式） | 基于已有 Analysis 上下文，流式返回追问回答 | `llm.ts` (chatWithAnalysis) + `chatPrompt.ts` |
| **`getCaseDetail`** | HTTP 调用 | 根据 caseId 返回案例完整数据（含 evidence + analysis），校验访问权限 | 无 |
| **`getCaseList`** | HTTP 调用 | 根据 openid 返回用户参与的所有案例列表，分页 | 无 |
| **`generateQRCode`** | HTTP 调用 | 调用 `cloud.openapi.wxacode.getUnlimited` 生成小程序码，返回云存储 fileID | 无 |

### 5.2 数据库集合设计

#### `cases` 集合

```
cases {
  _id: string                // 自动生成
  title: string              // 案例标题，默认"调解案例"
  relationship: string       // 情侣/朋友/同事/家人/其他，可选
  privacy: 'both' | 'initiator_only'  // 隐私设置
  party_a: {
    openid: string           // 甲方 openid
    nickname: string         // 甲方昵称
    avatarUrl: string        // 甲方头像
    submitted: boolean       // 是否已提交证据
    submittedAt: string      // 提交时间 ISO8601
  }
  party_b: {
    openid: string | null    // 乙方 openid（加入前为 null）
    nickname: string
    avatarUrl: string
    submitted: boolean
    submittedAt: string | null
  }
  status: 'waiting_party_b' | 'waiting_submission' | 'analyzing' | 'completed' | 'expired'
  analysisId: string | null  // 关联 analyses._id
  expiresAt: string | null   // 过期时间（P2）
  createdAt: string          // ISO8601
  updatedAt: string
}
```

#### `evidence` 集合

```
evidence {
  _id: string
  caseId: string             // 关联 cases._id
  party: 'party_a' | 'party_b'
  openid: string             // 提交者 openid
  rawText: string            // OCR 或粘贴的原始文本
  parsedMessages: [{         // parser.ts 解析结果
    speaker: string
    content: string
    timestamp: string | null
    type: 'text' | 'voice' | 'sticker' | 'image' | 'system'
  }]
  fileIds: string[]          // 上传截图/文件的云存储 fileID
  note: string               // 用户备注（可选）
  createdAt: string
}
```

**权限规则**：
- 读：仅 case 参与者可读自己的 evidence；分析完成后双方可读彼此 evidence（如隐私允许）
- 写：仅自己的 party role 可写入

#### `analyses` 集合

```
analyses {
  _id: string
  caseId: string
  schemaVersion: 'v2'
  
  // 完整 v2 Analysis 结构（复用 Web 版 schema）
  coreConclusion: CoreConclusion
  evidenceWeights: EvidenceWeight[]
  emotionCurve: EmotionCurve[]
  mediationStrategy: MediationStep[]
  detailedAnalysis: DetailedAnalysis
  advice: Advice
  
  // 进度信息
  progress: {
    step: string             // 'parsing' | 'understanding' | 'evidence' | 'emotion' | 'judging' | 'strategy' | 'done'
    message: string
    progress: number         // 0-100
  }
  
  createdAt: string
}
```

#### `invitations` 集合

```
invitations {
  _id: string
  caseId: string
  inviteCode: string         // 6 位数字码，唯一
  used: boolean              // 是否已被使用
  usedBy: string | null      // 使用者 openid
  createdAt: string
}
```

### 5.3 实时同步方案

```
┌──────────────┐         ┌──────────────┐
│   小程序端     │         │   云数据库     │
│              │         │              │
│  watch() ────┼────────>│  cases       │
│              │  变更推送 │  collection  │
│              │<────────┤              │
│              │         │              │
└──────────────┘         └──────────────┘
```

| 场景 | 实现方式 | 说明 |
|------|---------|------|
| **对方加入通知** | `cases` watch `party_b.openid` 变更 | 甲方页实时显示"乙方已加入" |
| **对方提交通知** | `cases` watch `party_b.submitted` 变更 | 甲方页实时显示"乙方已提交" |
| **分析进度** | `analyses` watch `progress` 字段 | 双方同时看到分析进度更新 |
| **分析完成** | `analyses` watch `progress.step === 'done'` | 双方同时看到报告生成 |
| **轮询降级** | 小程序 `onShow` 时主动拉取最新数据 | 作为 watch 不可用时的降级方案 |

**降级方案**：云数据库 `watch` 对小程序基础库有版本要求（≥2.9.0）。低版本设备降级为页面 `onShow` 时主动拉取（`getCaseDetail`）。

## 6. 与 Web 版的关系

### 6.1 可直接复用的代码（纯逻辑，无平台依赖）

| 源文件 | 小程序中对应位置 | 复用方式 |
|--------|-----------------|---------|
| `server/src/services/parser.ts` | 云函数 `uploadEvidence` / `analyzeCase` | **直接复制**，`parseWeChatChatLog` 和 `formatChatForLLM` 是纯函数，无 Node.js 特定依赖 |
| `server/src/services/llm.ts` | 云函数 `analyzeCase` / `chatWithAnalysis` | **核心逻辑复用**，云函数天然 Node.js 运行时。只需将 `process.env` 替换为云函数环境变量配置 |
| `server/src/prompts/analysisPrompt.ts` | 云函数 `analyzeCase` | **直接复制**，纯文本 Prompt 模板，零依赖 |
| `server/src/prompts/chatPrompt.ts` | 云函数 `chatWithAnalysis` | **直接复制**，同上 |
| `src/types/index.ts` | 小程序 `types/index.ts` + 云函数共享 | **直接复制**，纯 TypeScript 类型定义 |
| `src/utils/analysisMigration.ts` | 小程序 `utils/analysisMigration.ts` / 云函数 | **直接复制**，纯函数，用于处理可能的旧格式兼容 |

### 6.2 需要重写的部分

| Web 版模块 | 小程序替代方案 | 差异说明 |
|-----------|---------------|---------|
| **后端 Express 服务** | 云函数（Serverless） | 从持续运行的服务改为按需调用。天然适配，因为 Web 版本来就是无状态的 API 调用 |
| **内存 Map 存储** | 云数据库 `cases` / `evidence` / `analyses` | 从内存数据结构改为持久化 NoSQL 文档数据库 |
| **IndexedDB 本地存储** | 云数据库 + `wx.setStorageSync` | 案例列表和用户信息用云数据库，非关键缓存用本地存储 |
| **文件上传（multer）** | 云存储 `wx.cloud.uploadFile` | Web 版 multer → 本地 `/uploads`；小程序版 → 云存储 CDN |
| **OCR 调用** | 云函数调用 OCR API | 逻辑相同，但通过云函数中转（避免前端暴露 API Key） |
| **SSE 流式（chatWithAnalysis）** | 云函数 + 数据库轮询 / WebSocket | 小程序不支持原生 SSE。降级方案：云函数写入数据库 + 小程序 `watch` 逐条读取 |
| **React + MUI + Tailwind 前端** | 微信小程序原生 WXML + WXSS | 整个前端需要重写，但复用现有的 UI 设计语言和 4 层信息架构 |
| **文件拖拽/粘贴** | `wx.chooseMessageFile` / `wx.chooseMedia` | 交互方式不同，但流程相同 |

### 6.3 复用评估总结

```
可复用率（服务端逻辑）: ~80%
├── parser.ts              100% 可复用（纯文本处理）
├── analysisPrompt.ts      100% 可复用（纯 Prompt 文本）
├── chatPrompt.ts          100% 可复用（纯 Prompt 文本）
├── llm.ts                  90% 可复用（核心逻辑不变，仅配置方式微调）
├── types/index.ts         100% 可复用（纯类型定义）
└── analysisMigration.ts   100% 可复用（纯函数）

```
